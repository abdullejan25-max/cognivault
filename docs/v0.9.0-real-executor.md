## 为什么原先的阻塞现在可以解除

旧调查只确认完整 profile 会继承工具及私人配置。现在直接用安装程序导出的 Cordis 内核（组件容器）建立一个显式服务树，绕过 `dsh-app-boot`、profile、patch、`.env`、settings、sessions、skills 和 instructions 加载器。

实际只挂载：`LlmRuntime`、标准 `LocalCredentialProvider` 的只读子类、`AuthorizationService`、`PlatformAccount` 和一个选定的官方模型 provider。运行时检查没有 tools、filesystem、sessions、loader、settings、attachments、MCP、subprocess 或 terminal 服务。模型输出只作为字符串与 JSON 验证，从无工具执行循环。

凭据服务支持独立的 `path`。受信调用方显式提供既有授权文件位置，安装标准组件正常消费；本项目不调用 `credentials.resolve()` / `readRecord()` 来提取 token，不复制到环境、配置、日志或另一个服务。账号状态调查只读取标准服务返回的 `status`。后续模型认证由官方 provider 在同一正式 DeepSeek 服务内部完成。

标准凭据组件可能在初始化时自动迁移旧文件，账号组件可能删除发行者不匹配的 grant。因此只读子类明确阻断 `migrateFlatDocument`、`set`、`unset`、`modifyRecord`、`deleteRecord`、`write`，并关闭 watcher。若这些操作成为必要条件，执行器返回阻塞，不修改既有授权。没有为了得到一次回复而绕过它。

## 产品调用边界

```python
HarnessNoToolsAdapter(
    installation_root=operator_supplied_installation_root,
    credential_path=operator_supplied_credential_path,
    model="deepseek-flash",
    provider="deepseek-account",
)
```

安装路径、凭据位置、provider 和 model 是可信应用配置；不能从业务 Task、来源正文或模型输出选择。实现不扫描用户 profile。安装版严格检查 `0.2.1-rc.3`；升级后需要重新审查安装组件和接入版本。

- Python 以绝对 Electron executable 和独立 argv 启动 Node 模式；不用 shell、`dsh.cmd` 或命令字符串。子进程使用独立临时 cwd 与 home，环境只保留有限 OS 变量，不继承 API keys、proxy、TLS override 或 `NODE_OPTIONS`。
- 唯一供应商请求白名单为 `POST https://api.deepseek.com/anthropic/v1/messages`，拒绝重定向和额外请求；body 无工具/附件。全部实际模型材料都是自造 fixture。
- Task 必须再次通过 `external_allowed`、kind、capabilities 和大小校验。仅序列化显式 prepared；不会自动加入 `task.inputs`、工作目录文件、项目说明或用户会话。
- DomainHandler 构造的顶层 `task_guidance` / `expected_output_shape` 单独进入 `task_specification`；来源中的嵌套同名字段仍为不可信 context。Handler 必须自行覆盖可信规范，不能把任意来源映射直接当规范。
- stdin 与 stdout 上限各 1,000,000 bytes，stderr 上限 65,536 bytes。stdout/stderr 并行排空；总超时及取消结束进程。`process_guard.py` 在 Windows 先建立 kill-on-close Job（内核进程容器）并限制最多一个活动进程，再用 `CREATE_SUSPENDED` 创建应用、分配 Job、恢复初始线程。应用第一条指令执行前已经被限制，任何子进程创建均由 OS 拒绝；父进程先退出也必须关闭 Job。Job 配置、分配或恢复失败则不运行应用。POSIX 使用新 session/process group，父进程先退出仍按组清理。启动阶段取消会等待取得已创建的进程句柄再清理，不遗留挂起进程。
- 成功必须同时满足进程退出 0、无 stderr、唯一有效 JSON envelope、零工具隔离声明、供应商型号及双摘要、完整 Result 和任务绑定。不会把普通回复自动包装为可信 Result。
- 失败只暴露有限 `AdapterError` 代码。认证/隔离阻塞、速率限制、网络错误、超时、拒绝及无效响应分开；不把供应商正文、路径、reasoning 或凭据附在异常中。
- `healthy()` 仅判断本地程序前置条件；它不能证明认证或连接。`evidence_for(task_id, correlation_id)` 仅缓存最近 64 次成功调用的脱敏元数据，副本返回，不保存正文或 key。Receipt 的真实模型证据需要与域校验、Gateway 提交/回读证据分别判断。

## 标准 HTTPS 兼容路径

`HttpsChatAdapter` 直接使用 `httpx.AsyncClient`，启用证书验证，并以 `trust_env=False` 选择 HTTPX 的显式 certifi 根证书而不接受环境 CA 覆盖，不跟随重定向。默认只准 DeepSeek host，额外 host 只能由可信配置显式允许；endpoint 拒绝明文 HTTP、userinfo、query、fragment 和非 443 端口。认证仅来自指定环境变量，不搜文件、不用 GUI 凭据或 profile。

请求只有 model/messages/stream/max_tokens，无 tools。拒绝工具请求、截断、无绑定结果、重复 JSON key、非法数值、超限及压缩响应；请求 `Accept-Encoding: identity`，避免在限制前解压过大的数据。总超时和调用方取消直接抵达异步 transport，不留 `to_thread` 的不可中止请求。

```powershell
uv run --locked --extra dev python -m cognivault.orchestration.executors
```

当前实际输出为 `BLOCKED` / `AUTH_REQUIRED`、`model_invocation_verified=false`。这是本地缺少环境认证的前置判断，不是供应商返回 401。Harness 路径已可由标准授权组件调用，所以不能把该环境变量缺失再概括为整机“没有可用认证”。
